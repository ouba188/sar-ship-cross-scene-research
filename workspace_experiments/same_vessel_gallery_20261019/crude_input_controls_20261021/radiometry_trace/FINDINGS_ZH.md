## 结论与主端可用边界

**现有生成脚本支持“逐景、逐极化拉伸，然后裁片”，不支持“逐 chip 拉伸”。** 已从原始回传 manifest 将全部 400 视图关联到两套实际源目录及对应流水线脚本。两套脚本均显式传入 `--clip-percent 2 --pixel-size 10`；拉伸发生在完整 UTM 极化影像上，随后切网格和 chip 的代码均不重新拉伸。不过，各景实际数值下限 lo、上限 hi，以及当时远端可执行脚本的版本与逐景执行记录，未取得完整证明。应写成“存档流水线是逐景拉伸”，不能写成“400 视图的历史上下限已恢复”。

**本次没有恢复任何拉伸前浮点 chip，也没有恢复任何已定标 backscatter。** 实际获得的两类上游像素是：已经拉伸过的 UInt8 TIFF 缓存，以及 SAFE measurement 中未定标的 UInt16 DN。二者不能混称“原始辐射值”。

主端新增的目标区/其余区域 ±0.05 操作，应解释为 **PNG 数值域的功能诊断**，不是改变物理散射或海况，也不能据此证明变化来自逐 chip 归一化。若 ±0.05 施加于 `[0,1]` PNG，它对应 ±12.75 个显示灰度级；实施时的截断或量化以主端实际代码为准，本分支没有运行这些干预。

## 来源链与拉伸算法

两套路径分别对应 130、270 视图：

1. `/root/autodl-tmp/sar_download_v1/...` → `asf_ais_first_screen_20260913/server_zip_pipeline.sh`。
2. `/root/autodl-tmp/asf_download_v2_tmp/...` 或同系列旧目录 → `asf_ais_first_screen_20260913/server2_zip_pipeline.sh`。

两者调用 `v5_server_toolkit_20260912/scripts/sentinel1_geocode_manifest.py`，顺序如下：

```text
SAFE measurement TIFF
  -> gdal.Warp：UTM、10 m、nearest、UInt16
  -> 整景该极化 band 的近似 min/max 与 4096-bin 近似直方图
  -> 每端 2% 分位所在直方图 bin 推出 lo/hi
  -> gdal.Translate(scaleParams=[[lo,hi,0,255]], outputType=Byte)
  -> UInt8 整景 TIFF
  -> 4x4、overlap=256 的网格 TIFF（读取窗口并原值写入）
  -> 原 crop manifest 的方窗
  -> PNG（原值裁片/编码）
```

算法不是对每个 ship chip 求 2/98 分位：它先在整景单极化 band 计算近似直方图。设整景近似范围为 `[m,M]`，步长 `s=(M-m)/4096`，累计直方图达到 2%、98% 的 bin 为 `i_lo,i_hi`，则存档实现使用 `lo=m+i_lo*s`、`hi=m+max(i_hi,i_lo+1)*s`。常值景另有 `hi=lo+1` 分支。VV、VH 分别计算，所以不同极化也不能默认共享灰度尺度。

存档代码没有在此流程应用 calibration LUT、输出 sigma0/gamma0 或转换到 dB。中间 UInt16 UTM TIFF 及其 sidecar 在地理编码后被删除，外层流水线在成功后也删除 ZIP。这解释了为何可能只留显示产品，但**不能凭代码就断言各远端文件现已删除**；当前远端状态未知。

`CODE_EVIDENCE.md` 保存带原路径/行号的真实脚本摘录。两个 crop 实现分别用 Pillow `image.crop(...).save(...)` 和 GDAL `ReadAsArray(window)` + PNG `CreateCopy`，均无逐 chip min/max、percentile、log 或 gamma。170 个去重的原 source JSON 也已检查，未发现 stretch/percentile/radiometry/calibration 上下限字段；该检查不声称覆盖世界上所有日志。PNG header、可用 TIFF header 和已查 sidecar 均未补齐历史 lo/hi。

原来不能区分的两件事现在可以分开：

- “是否在裁 chip 时重拉伸”：现有管线证据明确为否，30 视图还有源缓存逐像素支持。
- “跨景灰度是否可直接作物理量比较”：不能；存档管线逐景求上下限，实际 lo/hi 不可得，且数据已经量化和截断。

## 实际小窗口核对

UInt8 缓存来自 `E:/safe841_local_20260918` 中两景、496 个可用小 TIFF。只读其 header，按产品/极化和 CRS/像元格网/地理变换定位覆盖 chip 的缓存，再读取 chip 大小窗口。52 次含重叠窗口的比较对应 32 个独立视图，重叠副本不当作额外独立证据。

其中 27910 的两极化各差 1 像素：VV 在 chip `(x=49,y=4)`，PNG=14、缓存 TIFF=26；VH 在 `(43,1)`，PNG=47、缓存 TIFF=45。两处均在 R 区，两个重叠缓存窗口对各自数值一致。根因未明，缺少服务器原 TIFF 可作裁决，故保留为非 exact，未改任何像素。见 `sparse_pixel_mismatches.csv`。

两景可读 SAFE 为 Port Klang 产品尾码 122F、CEA9，共 11 端点、22 视图。header 明确为 **UInt16**，带 210 个 GCP，单行 strip；未取得经过定标的浮点产品。使用已存 chip 地理变换把像元中心反变换到 measurement，读取包围的原生小窗并做 nearest 采样。最大窗口仅 113×112，总请求 188,266 原始像素。底层 TIFF 单行 strip 宽 25,412，因而估计实际条带解码量约 101.85 MB，不能把请求像素数冒充磁盘实际读取量；没有整景解码。

这批映射窗口内实际 DN 范围为 VV 13–6951、VH 5–1960；这只是所读窗口的范围，不是整景极值。22 视图的像素级 Spearman 相关为 0.9578–0.9950，支持图像内容的空间对应，但不是历史每个输出像素的精确重放。原始整景 warp 的近似变换、GDAL 执行版本及确切上下限仍有缺口。`source_pixel_comparisons.csv` 中的线性拟合系数仅用于诊断 DN 与 PNG 的对应，不是保存下来的 lo/hi，也不应反推成真实拉伸参数。

`source_window_statistics.csv` 分别记录已 UInt8 窗口统计和未定标 UInt16 DN 候选的全图/T/R 统计；`raw_window_mappings.json` 记录源路径、原生窗口、输出格网与恢复方法。`raw_candidate_pixels.png` 回看 21799 和 32937 的 VV/VH：主要亮结构空间位置对应，但幅度显示有差异。图中 DN 专门用新计算的局部 2/98 分位可视化，并明确标注上下限；**这只是本报告的展示，不是对历史预处理的复现或证据**。
